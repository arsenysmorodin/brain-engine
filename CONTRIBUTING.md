# Участие в NeuroLab

Спасибо за вклад в код, интерфейс, документацию и проверяемые научные данные. Для начала прочитайте [README](README.md), [архитектуру](docs/architecture.md), [научный статус](docs/scientific-status.md) и инструкции [AGENTS.md](AGENTS.md).

## Issue и обсуждение

Для ошибки укажите commit SHA, ОС/архитектуру, `rustc --version`, шаги или CLI-команду, минимальный сценарий, ожидаемый/фактический результат и stderr/скриншот. Не публикуйте частные данные или секреты.

Для научного расхождения приложите первоисточник, конкретную таблицу/рисунок, единицы, вид/выборку, тип статистики и способ сравнения. Средние индивидуальных пиков нельзя без объяснения сравнивать с пиком средней кривой. Для предложения возможности опишите пользовательскую/исследовательскую задачу и наблюдение, которое позволит проверить результат.

## Разработка

1. Создайте тематическую ветку от актуального `main`.
2. Сохраняйте границы crates: прикладной/научный код на Rust; Bevy/egui только в `neuro-app`; единый вычислительный путь GUI и CLI.
3. Сохраняйте Cargo.lock и бюджет сборки два jobs. Не обновляйте зависимости попутно с несвязанным изменением.
4. После значимых изменений выполняйте подходящую проверку и делайте сфокусированный коммит. Не отправляйте ветку/данные во внешние сервисы без авторизации владельца.
5. Обновляйте связанные руководства, примеры, схемы и историю совместимости.

[Установка, проверки и нативные smoke-сценарии](docs/development.md).

## Научные изменения

Новая формула требует идентификатора/ревизии модели, уравнений, единиц, допущений, источников и области применимости в документации. Добавьте аналитический предел или независимый вычислительный эталон, численную сходимость, баланс/причинность, где применимо. Проверьте старые сценарии и фактическое совпадение GUI/CLI.

Разделяйте измерение, предположение, подгонку и гипотезу. Неизвестное не заменяется нулём. Ki/IC50/EC50 не подставляются вместо Kd. Занятость не равна активации; E/I не равно поведению. Хорошее совпадение на обучающих точках не является независимой валидацией. Отрицательный результат, неидентифицируемость и отсутствие данных — полезная часть научной документации.

Новые данные должны иметь происхождение, контекст, вид, условия, права и фактический статус проверки. Для оцифровки нужны исходные оси/координаты/неопределённость; не выдумывайте закрытые/перекрытые точки. Не добавляйте целые статьи/изображения или частные записи без соответствующих условий.

## Перед pull request

```sh
cargo fmt --all --check
cargo test --workspace --locked
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo build --workspace --locked
cargo doc --workspace --no-deps --locked
git diff --check
```

Для GUI отдельно запустите релевантный native smoke и просмотрите скриншоты. Для документации выполните примеры и проверьте относительные ссылки. Не считайте сборку визуальной проверкой. Не коммитьте `.local/`, `target/`, `output/` и личные проекты; публикуемые демонстрационные сценарии должны быть намеренными и обезличенными.

В PR объясните проблему и итоговое поведение, перечислите релевантные проверки, изменения совместимости и научные ограничения. Для простого изменения достаточно короткого описания; для формулы нужны источники и верификация. Сохраняйте атрибуции ресурсов. Отдельные GitHub Actions/релизы не считаются настроенными без их реального выполнения и проверки.
